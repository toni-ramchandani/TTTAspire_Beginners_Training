What token tests can prove

Context fit, prompt growth, truncation boundaries, approximate request size and output space remaining.

What they cannot prove

Meaning is not a token count

Fewer tokens do not imply a clearer, safer or more correct request.

Do not teach: one token equals one word. Tokenisation depends on the selected encoding. Provider-reported usage remains authoritative for the completed request because message framing and other fields may add tokens.

SequenceMatcher measures normalised surface text, not semantic similarity. The 0.30 label-pair value is not inter-rater agreement. These values belong to five prepared examples and are not production reliability estimates.

Analysis questions
  1. Why is Run 3 semantically correct but unusable by a strict parser?
  2. Why does Run 4 remain release-blocking despite five passing checks?
  3. What evidence is required before claiming a 40% production pass rate?
Evaluator limitations

Narrow regular expressions catch known phrases such as “I reset” or “emailed password.” A paraphrase such as “The login secret has been delivered” may escape them. Passing the regex does not prove every unsafe paraphrase is absent.

For production reports, prefer pass, fail and not_evaluated when parsing blocks downstream checks.

  2. outputs = collect_live_outputs(case, model, mode, value)
